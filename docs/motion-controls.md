# Logical motion controls and local settings

Pythonic output supports `HOLD`, `UNHOLD` and `CANCEL` through the explicit
[MotionRequests](motion-requests.md) and [GroupLocks](group-locks.md) services.
Eleven temporary `WITH` settings can accompany any supported MOVE form. These are
offline state and request models. They do not compute trajectories, operate
physical hands, change robot feedback or reproduce controller timing.

## Hold flags and work labels

GroupLocks keeps two independent values for each configured group:

- `motion`: the existing `idle`, `executing` or `stopped` logical work label.
- `held`: a separate flag preventing new MOVE requests for that group.

| Action | Work label | Hold flag |
| --- | --- | --- |
| `HOLD` | Preserved, including stopped work | Set, even when idle |
| `UNHOLD` | Preserved | Cleared |
| `CANCEL` | Executing becomes idle; stopped and idle remain unchanged | Preserved |
| `CNCL_STP_MTN` | Caller-owned stopped labels become idle | Preserved |

For example, canceling a held active group clears its active label but leaves
the hold in place. Explicit UNHOLD is still required before a new MOVE. A MOVE
while held raises before recording the request or consuming a response; this
model does not queue the move or wait for another task to unhold it.

The work labels are supplied by the host, rather than generated by trajectory
execution. Capture-only and immediate scripted moves retain their existing
zero-duration default. [Local clauses and supplied delays](motion-handlers.md)
can retain an active synchronous scope. Controls update the explicit logical state and record
completed control requests. They consume no scripted MOVE response.

## Group selection and handlers

```karel
LOCK_GROUP(3,status)
HOLD GROUP[1,2]
CANCEL GROUP[1]
UNHOLD GROUP[1,2]
```

An explicit `GROUP[expression,...]` selects distinct configured integer group
numbers, with at most 31 entries. Expressions are evaluated once from left to
right. All ownership, address, capacity and history checks complete before any
selected group changes. An unowned or foreign group rejects the entire action.

An omitted GROUP selects all groups owned by the current calling root **when
the action executes**. A selection with no owned groups records a successful
no-op. This action-time policy also applies inside global condition handlers;
it does not freeze ownership at handler definition time. EVAL remains available
for explicitly captured source expressions.

The three controls and hand statements are accepted global and
[motion-local](motion-handlers.md) handler actions.
Logical hands may change while their owned group is active or held; hand state
does not alter the work label or hold flag. Linked routines and called programs
retain the calling task's ownership and record the originating source module.

ATTACH, RELEASE and MOVE require idle, unheld selected groups. RELEASE does not
implicitly cancel a held group. UNLOCK_GROUP retains held owned groups: it
returns 17040 for stopped work and 17039 for other held or active work. These
hold-related unlock results are an explicit extension of the offline model.
Automatic root/callee acquisition cannot acquire an unowned held group.
Explicit LOCK_GROUP can acquire available busy/held labels for subsequent
control actions, retaining its existing partial acquisition behavior.

Root completion, stop, abort or failure releases ownership while preserving
the supplied labels and resulting hold flags. A new task needs explicit
ownership before changing those flags. Source frames and task ownership are
never restored from JSON.

## Temporary WITH settings

```karel
WITH $SPEED=250, $MOTYPE=LINEAR, $USE_CONFIG=FALSE
MOVE TO target
```

| Setting | Accepted request value |
| --- | --- |
| `$SPEED`, `$ROTSPEED` | Finite nonnegative numeric value, captured as Python float; no inferred native speed limit |
| `$MOTYPE` | JOINT, LINEAR/STRAIGHT or CIRCULAR; equivalent INTEGER expressions 6, 7 or 8 |
| `$TERMTYPE`, `$SEGTERMTYPE` | FINE, COARSE, NOSETTLE, NODECEL or VARDECEL; INTEGER values 1 through 5 |
| `$ORIENT_TYPE` | RSWORLD, AESWORLD or WRISTJOINT; INTEGER values 1 through 3 |
| `$UFRAME`, `$UTOOL` | Complete Cartesian POSITION, XYZWPR or XYZWPREXT value, detached with its explicit representation |
| `$USE_CONFIG`, `$USEMAXACCEL` | BOOLEAN, without numeric truthiness |
| `$DECELTOL` | INTEGER 0..99; zero unspecified default intent, 1..99 percentage intent; see [deceleration settings](motion-deceleration-settings.md) |

Each setting optionally accepts a group expression, for example
`WITH $SPEED[group_number]=speed_value MOVE AWAY distance`. It must resolve to
the same group as the MOVE request. Cross-group motion settings and duplicate
settings are rejected. At most eleven entries are accepted. The explicit
`$GROUP[group].$NAME` spelling and new enum choices follow
[extended motion settings](extended-motion-settings.md).

For each entry, its group expression is captured first, then its value. Entries
are evaluated in source order, before the MOVE operands. Frame/tool data is
detached immediately, so a later setting or destination expression cannot
retroactively change it. Completed source-expression side effects remain if a
later validation fails; work labels, hold flags, history and response consumption remain unchanged until
request preflight succeeds. Normal terminal ownership cleanup still applies.

The setting data belongs only to that request. It does not write system
variables, set RobotContext frames, transform destination coordinates or carry
over to the next MOVE. No default motion environment is discovered. MOTYPE,
termination and orientation names are contextual within their corresponding setting; this does
not add global constants or an arbitrary system-variable namespace.

Explicit CIRCULAR requires MOVE TO with VIA. An explicit JOINT or LINEAR setting
conflicts with VIA. Existing VIA requests without a supplied motion type retain
their capture contract; the runtime does not infer interpolation or geometry.

## Persistence and reports

GroupLocks JSON adds `"held": [1, 2]` only when the set is nonempty. Old configs
and canonical output with no holds remain unchanged. Live ownership still
prevents saving. Completed tasks can save hold flags and work labels as logical
state; no previous task grant is recreated.

Control history records the selected groups and each group's before/after work
label and hold flag. Restoring history checks the transition rules. MOVE history
adds a bounded `settings` list containing name, group and detached value. Unknown
fields, malformed typed values, duplicate settings and invalid groups fail to
load. The existing 64 KiB request and history/sequence bounds still apply.

Translation reports extend `motion_request_policy` with control/setting rules
and add setting source locations to the affected `motion_requests` entries.
Source maps retain physical include origins.

See the authored [controls](../examples/motion_controls.kl),
[handler](../examples/motion_control_handler.kl),
[settings](../examples/motion_with_settings.kl) and
[linked calls](../examples/motion_control_project/main.kl).
Local [Boolean WHEN/UNTIL and finite delayed responses](motion-handlers.md) are
supported through synchronous scopes. [Local node/time predicates](motion-timeline.md)
use complete supplied schedules. NOWAIT queues, inferred arrivals, remaining WITH
variables, global system-variable access and native synchronization remain unsupported.
